# 共通の警告通知と旧PC専用データの確認

## 目的と適用範囲

処理の最終失敗は既存の[共通エラー通知](error-reporting.md)で扱う。処理失敗が確定していなくても利用者の確認・対処が必要な状態には、本体の共通「警告通知」を使う。最初の接続先は旧PC専用データの残存検出とする。入力途中の検証、通常の情報、既存の再起動要求を一括移行しない。

既存のNotificationService / TypedNotifications、通知履歴、Shell、Windows表示、読み上げ、共通ログへ接続する。別の通知配信経路や保存ファイル、MCP / Applet向けの任意警告発行APIは追加しない。

## 種類と利用者の設定

識別子は `host / warnings / attention-required`、レベルはwarning。通知設定のAppDock欄で「エラー通知」「警告通知」の順に表示する。既定はON、バナーとデスクトップ通知、閉じるまで表示、読み上げOFF。表示先・時間・読み上げを既存の `notificationPreferences.overrides` で変更する。バナーを必須とし、バナー解除とセンターのみは選択できない。通知全体のOFFは設けない。旧設定のバナー不足は実効方針で補い、読み込みだけでは保存しない。エラー通知、設定の再起動要求から独立させる。

## 共通入口と状態の寿命

本体内部の `WarningReporter.episode()` を使う。発行元がeventId/source/title/code/messageと必要な操作を渡す。通知と履歴には短い原因・対処・警告コードを保存する。診断情報 `logDetails` は発行元が安全性を確認した固定説明とローカルパスだけを渡し、通知・履歴・読み上げには含めない。例外本文、JSON本文、Cookie、認証情報、ファイル内容、対象内のファイル名一覧は収集しない。

- 同じ状態の再評価・画面の往復・再描画は新規発行にしない。
- 原因や対象が変わった場合だけ共通ログのwarningレベルへ記録する。各対象を独立したログ行にし、全体の切り詰めで後半の対象を失わない。
- アクティブ通知の内容更新は同じID・期限を維持し、読み上げを再発行しない。
- 閉じる・期限切れ・配送失敗後は、同じ状態の間に復活させない。本体ログの状態は更新する。設定の変更で過去の警告を再送しない。
- 状態が解消したら発行元がresolveし、現在の通知だけを終了する。その後の再発は新episodeにする。
- 起動中のepisodeはメモリーだけに置く。次回起動時は現状を再評価し、残っていれば新規に通知する。再起動をまたぐ既読管理用の保存ファイルは追加しない。
- 通知・ログ自体の障害を再帰的に警告通知へ流さず、元の処理を失敗にしない。

## 旧データの検出と詳細

EXE隣の `data` と `.appdock` について、`chromium`、`web-accounts`、`storage`、`secrets`、`web-applets/sessions` の存在だけを調べる。空のフォルダーも対象とし、内容は読まない。settings.jsonの値を検出条件にしない。従来の隔離テストで共有rootと実行rootが同じ場合は対象外とする。

起動準備後に検査し、以後2秒間隔で更新する。存在しないパスと検査不能を区別する。検査不能な状態では以前の対象を保持し、未検出・解消とは表示しない。通知コードは `LEGACY_LOCAL_DATA` / `LEGACY_LOCAL_DATA_UNREADABLE`。

通知の「詳細を見る」は既存の入力反映・ナビゲーションを通って本体ログを開く。一般設定には旧PC専用データの専用欄を置かない。実際のパスは本体ログの「整理対象」へ記録する。既存の内部状態・HostSnapshotのbooleanは保持し、rendererの独自エラーバナーは使わない。

## 整理と削除の判断

今回は通知からの自動削除を実装しない。旧ログイン・認証・Applet状態を含むため、完全終了・バックアップ・利用状況の確認を経て手動で整理する。通知のボタンは対象の確認へ誘導する。トレイ常駐を終了と扱わない。

settings.json、data全体、登録素材、共有名簿、現在のLOCALAPPDATA配下のPC専用rootを削除対象にしない。`.appdock`にも従来の画像参照があり得るので全体削除を案内しない。検出対象がリンク等の場合も自動でリンク先をたどって削除しない。旧WebログインとGmail枠を引き継がない既存の方針を維持する。

将来ボタンで削除する場合は、今回の検出結果だけを削除許可に使わず、終了後の実行、最新状態の再照合、対象境界とリンクの検査、対象を明示する確認、失敗時の保全を別途設計する。

## 検証と版

警告の独立した設定、既定値、抑止と再ON、閉じる・期限切れ、同一IDと期限、原因・対象の変更ログ、解消・再発、報告経路自体の障害を単体で確認する。旧データの固定範囲、空ディレクトリー、除外する共有素材と現在の保存先、検査不能、ファイル不変を確認する。

隔離したElectron / 発行済み固定EXEで、警告の描画、詳細ボタンから本体ログへの移動、フルパスのログ記録、通知設定の保存、再表示抑止、定期検査と解消、対象データの不変を確認する。実利用データの整理や実同期サービスの動作試験とは区別する。

警告通知の設定項目を追加するため本体を0.47.0へ更新する。未変更Appletの版は変更しない。実測とレビュー結果は[検証記録](../VERIFICATION.md)に残す。
