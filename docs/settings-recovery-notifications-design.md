# 設定ファイルの受信・復旧と再起動通知の設計

状態: 設計案。製品コードは未変更で、通知と復旧導線の追加は未実装。

調査基準: `main` の `61dca8477069dad12f0c6f8ef4605bebeb30da99`（0.37.1）。別作業の未コミット変更を取り込まず、専用worktreeで設計する。実装開始時に設定・通知・再起動の現行コードとの差分を照合する。

現行契約は[設定同期](settings-sync.md)、[設定基盤](settings-foundation.md)、[通知基盤](notifications.md)、[Windows起動設定](launch-settings.md)を参照する。この文書は追加する動作と、その実装・検証計画を定義する。

## 1. 要求と採用方針

- EXE隣の `settings.json` に同期で届いた正常な設定を採用する。別PCの変更と、このPCの変更を保存して自動統合する3方向マージは導入しない。
- AppDockからの妥当な変更は即時保存する。外部更新は読み直して実行中のAppDockへ適用する。
- 設定の変更を反映するために再起動が必要な場合、理由を通知基盤へ表示する。
- 設定の読み込み・保存などで処理上のエラーが起きた場合も、理由と必要な対処を示して再起動を案内する。再起動だけで直るとは断定しない。
- 両方の通知に「再起動」ボタンを置く。自動では再起動しない。
- JSONが壊れた場合に、正常なバックアップから復元できるようにする。壊れた内容は復元前にPC内へ退避する。
- 同じ問題で通知を増殖させず、問題が解消したら終了する。通知のために共有ドラフト・dirty・全体保存/破棄を復活させない。

本設計の「設定エラー」は保存先・受信ファイル・バックアップ・設定保存処理の障害を指す。編集中の不完全な数値やJSON、入力値の検証違反、古いrevisionの拒否は、現在の入力欄で説明する。通常の入力修正まで再起動通知の対象にはしない。

## 2. 現在の実装と追加する部分

| 対象 | 調査基準での実装 | この設計での扱い |
| --- | --- | --- |
| 外部設定の受信 | 親フォルダーの監視と2秒のpoll、安定した内容を検証して採用 | 維持 |
| 同時保存の保護 | 保存直前のファイル照合とrevision検査 | 維持。古い操作を自動で再試行しない |
| 実行中への反映 | `SettingsStore.changed` からテーマ・トレイ・キー・Applet等へ反映 | 維持 |
| 正常設定の保存 | PC専用の `last-good.json` と直近20世代 | 維持し、復旧時の候補に使用 |
| 起動時の破損 | 正常バックアップがあれば、その設定で動作を継続 | 継続状態を通知する |
| 共有ファイルの復元 | `restoreBackup` と確認dialogを呼ぶ既存IPCあり | 通知からも同じ復元処理へ接続する |
| エラーの画面表示 | ホストの `syncError` バナーに復元ボタンあり | 全体バナーは通知へ統合し、一般設定に状態・復旧導線を残す |
| 正常設定を得られない起動 | エラーdialogを表示して終了 | 最小の起動時復旧dialogを追加する |
| 再起動待ち | GPU設定の変更は次回起動で適用。専用通知はない | 起動時の適用値との差分から通知する |
| 設定の処理障害 | `syncError`、ログ、各操作のエラー | 分類可能な状態を追加し、通知へ投影する |

## 3. settings.jsonを優先する範囲

### 3.1 外部ファイルの取り込み

1. 安定した内容を読み取り、JSON構文と設定schemaを検証する。
2. 正常なら保存済み設定をその内容へ更新する。このPCの以前の設定との差分を保存して戻さない。
3. 既存のchanged経路へ通知し、即時反映できる項目を適用する。
4. 再起動待ちと設定障害の状態を再評価する。

正常な受信だけを理由にファイルを整形・書き戻ししない。同じ内容の受信や自分の保存を再検出しても、通知を再発行しない。

保存直前に未反映の外部更新を検出した場合は、現在どおり外部ファイルを採用して古い保存要求を拒否する。画面内の不完全入力・競合表示の保持方針は[設定基盤](settings-foundation.md)に従う。入力を黙って破棄するUI変更は本設計に含めない。

ファイルの優先は「同期サービスがこのPCのsettings.jsonへ置いた内容を採用する」という意味であり、編集日時が一番新しい版の判定ではない。別名の同期競合コピーの自動取込、PC間の変更履歴、同期サービスの設定変更は行わない。

### 3.2 不正・欠落・一時的ロック

不正なファイルを設定値として採用せず、最後の正常値で動作を継続する。自動で初期値を書き戻したり、破損ファイルを削除したりしない。

監視による一時的な失敗は現在どおり記録するが、通知は障害が2秒継続した場合に発行する。短時間で正常に戻れば通知しない。保存要求の確定した失敗と、起動時に判明したバックアップ継続状態は待機せず通知対象にする。

通常保存の原子的置換とrevision保護は維持する。これらを、任意の外部プロセスとの完全な排他やPC間の同時書き込み保証とは扱わない。

## 4. 再起動が必要な設定の判定

### 4.1 最初に対象とする設定

`host.hardwareAcceleration` を対象とする。Electronへ起動前に適用した設定値を、このプロセスの基準値として保持する。現在の保存済み値がその基準値と異なる間だけ再起動待ちにする。

実行環境のGPU対応可否や描画のフォールバックを「設定変更」と誤認しないため、判定基準は起動時に要求した値とする。実際のGPU状態は検証で別途確認する。

| 変化 | 動作 |
| --- | --- |
| 起動値と同じ | 通知なし |
| 画面/API/外部ファイルから異なる値へ変更 | 理由付き通知を開始 |
| 再起動前に起動値へ戻す | 通知をresolvedにする |
| 再起動して保存済み値を適用 | 新プロセスでは通知なし |
| 無関係な設定だけ変更 | 通知ID・状態を維持 |

起動時の基準値は3方向マージのbaseではなく、再起動待ち判定に必要なメモリー内の値だけである。追加のbaseファイルを作らない。

### 4.2 次回起動方針との区別

`startMinimized`、更新の起動時確認、Appletの起動遅延などは次の起動時の動作を指定する設定であり、変更だけで現在のプロセスを再起動必須にはしない。Applet設定は既存のsettingsChanged契約を使い、宣言のない項目を本体が勝手に再起動対象へ分類しない。

`runAsAdministrator` も次回起動方針として既存仕様を維持する。管理者起動の失敗は設定エラーの説明対象になり得るが、一般の再起動ボタンに自動的な昇格・降格を追加しない。「管理者として再起動」は既存の専用操作を使う。管理者プロセスの通常再起動は権限を引き継ぐため、OFFへの変更については「完全終了して通常権限で起動」を案内する。

外部JSONで `startAtLogon` が変わってもWindowsのタスク登録を自動で変更しない。再起動で登録まで完了すると案内しない。

将来、ほかに実行中へ適用できない設定を追加した場合は、理由・起動時適用値・解消条件を登録する。本体の設定全体を比較して再起動通知を出す方式にはしない。

## 5. 設定エラーの分類と解消条件

内部状態は表示文字列だけで判定せず、障害の種別、保存済みrevision、発生/更新時刻、処理世代、安全な説明を持つ。設定値や途中入力そのものは保持しない。

| 種別 | 通知に示す理由と対処 | 解消条件 |
| --- | --- | --- |
| `read-invalid` | JSON構文/schemaが不正。バックアップで動作中ならその旨を表示。ファイルを修正または復元し、必要に応じ再起動 | 正常な受信または復元完了 |
| `read-unavailable` | ファイルの欠落・読み取り権限・継続するロック。保存先を確認して再起動 | 正常な読込 |
| `save-failed` | 設定保存を完了できなかった。変更が保存されたとは表示しない。保存先を確認し再起動後に再設定 | 同じ保存系統の後続処理成功、または再起動後の再評価 |
| `backup-failed` | 設定の読込/保存は成功したがPC内バックアップを更新できない。空き容量・権限を確認して再起動 | 実際のバックアップ保存成功 |
| `apply-failed` | 設定は保存/受信できたが、関連するホスト機能への反映を完了できない。対象機能と理由を示し、再起動を案内 | 対象機能で現在の設定の反映成功 |
| `launch-save-failed` | Windows起動設定の変更・復元処理で障害。登録状態を確認して再起動 | 再確認と必要な保存処理の成功 |

UACの明示キャンセル、入力検証、revision競合、操作中のBUSYは処理障害と分け、操作元の説明を維持する。設定と無関係なAppletの異常終了や通信障害をこの通知へ混ぜない。

同時に複数の障害がある場合は設定エラー通知1件に集約し、未解消の理由を列挙する。一つの正常受信で保存失敗やバックアップ失敗まで一括解除しない。非同期処理の古い失敗結果が新しい成功を上書きしないよう、処理世代を照合する。

反映失敗は既存の各機能が返す設定適用結果を使い、保存済みrevisionと対象機能を対応付ける。たとえばショートカットのOS登録失敗を、保存失敗や正常な一時登録解除と混同しない。機能別の詳細表示は維持し、無関係な実行エラーをまとめて設定障害へ変換しない。

OS例外・JSON本文・APIキー・URLなどを通知本文や履歴へそのまま転記しない。原因は処理段階と既知のエラー分類から安全な文言へ変換する。詳細ログの既存方針も維持する。

## 6. 通知の種類・表示・寿命

`notificationCatalog` に次の本体通知種類を追加する。設定ページへの項目追加は既存カタログからの生成を使う。

| 項目 | 再起動待ち | 設定エラー |
| --- | --- | --- |
| ownerKind / ownerId | `host` / `settings` | `host` / `settings` |
| typeId | `restart-required` | `error` |
| 設定上の名前 | 設定変更による再起動の案内 | 設定の読み込み・保存エラー |
| レベル | warning | error。バックアップ単独の失敗はwarning |
| 既定表示先 | banner | banner |
| 許可する表示先 | banner / desktop / windows | banner / desktop / windows |
| 寿命 | condition | condition |
| 無効化 | 可能 | 可能 |
| 履歴 | persistent、安全な要約だけ | persistent、安全な要約だけ |
| 読み上げ | 既定OFF | 既定OFF |

無効化・表示先・読み上げは既存の種類別設定を使用する。新しい専用設定ファイルは作らない。conditionのため時間経過や閉じる操作では解消しない。通知を抑制しても、設定のエラー状態や入力画面の説明は消さない。

現在のホスト全体の `syncError` バナーは通知へ統合し、同じ障害を二重に表示しない。一般設定に「設定ファイル」の状態と復旧操作を置き、通知を無効にした場合も確認・復元できるようにする。保存先の詳細や復旧操作はここに集約し、入力欄固有の検証エラーはその欄に残す。

表示例:

```text
再起動が必要です
ハードウェアアクセラレーションの設定が変更されました。
保存した設定を反映するため、AppDockを再起動してください。
[再起動]
```

```text
設定を確認して再起動してください
settings.jsonの形式が不正なため、このPCの正常なバックアップで動作しています。
ファイルを修正するか、バックアップから復元してください。
再起動だけでは、壊れたファイルは修復されません。
[再起動] [バックアップで復元] [保存先を開く]
```

設定エラーのタイトルは、再起動の案内と修正の必要性を両方示す。「再起動すれば必ず修復される」という表現は使わない。正常な再受信で解消した場合は、再起動を強制せず通知を終了する。

### 6.1 重複と状態遷移

- 通知種類ごとに固定のdedupeKeyを使い、同じ問題は同じactive通知を更新する。
- 理由・操作可否に変化がなければpublishしない。poll、画面更新、既読変更だけでは再発行しない。
- 条件が解消したらresolved。再び発生した場合は新しいepisodeとして新IDを発行する。
- 設定で無効にした通知はwithdrawn。再度ONにしただけで同じepisodeを復活させず、次の発生から通知する。抑制済みepisodeは発行元がメモリー内で識別する。
- 表示先変更はTypedNotificationsの既存reconcileを使い、通知IDを保つ。
- 再起動後は旧active履歴を既存どおりinterruptedにする。現在の設定とエラーを再評価して、なお問題がある場合だけ新規通知を発行する。
- 終了時は発行元を先に停止し、購読・遅延タイマー・操作を解放する。通知サービスの終了後に発行しない。

## 7. 再起動ボタン

本体が発行する通知actionとして `key: restart`、`label: 再起動` を設定する。rendererへ任意コマンドや関数を渡さず、既存の通知action ID、revision、requestId検査を使う。

処理は現在の `appdock.restart` / `quitHost(true)` と同じ経路を使い、元の単一EXE、profile、`--restore-view`、終了時のApplet停止を保持する。通知からの再起動のために、途中の入力や保存失敗値を強制保存しない。

実行中の保存・復元トランザクションがある間はボタンをbusy/disabledにし、終了処理との競合を避ける。基盤の通知単位の操作排他に加え、ホスト全体で多重再起動を防ぐ。別通知から押された場合も起動プロセスは増やさない。

保存先の修正が必要な場合でも再起動ボタンは用意し、本文で前提条件を伝える。ボタン押下だけでエラーをresolvedにせず、終了・新プロセスの状態に従う。再起動の手配が失敗した場合は動作中のAppDockを保持し、同じ通知に操作失敗を表示して明示的な再試行を可能にする。

バナー・独立デスクトップ・通知センターにはボタンを表示する。Windows通知は既存契約に合わせ、クリックで通知センターを開き、そこで「再起動」を押す。OS通知のクリックだけで再起動しない。Windows固有のボタン追加はこの設計に含めない。

## 8. JSON破損からの復旧

### 8.1 正常なバックアップがある場合

既存のPC専用 `settings-backups/last-good.json` と直近20世代を使う。起動時は候補を再検証し、最新の読み取り可能な正常設定で動作を続ける。実行中の破損では最後の正常値を保持する。共有ファイルは自動では修復せず、設定エラー通知に「バックアップで復元」を表示する。

復元ボタンは本体の共通復元処理へ接続し、既存IPCと通知で別実装にしない。最初の実装では最新の正常候補を使用し、過去世代の選択UIは追加しない。操作可否は `recovered` だけで判断せず、正常な復元候補の存在と現在の障害分類を確認する。

復元手順:

1. 復元する候補を再読込・検証し、確認画面にバックアップ日時と「同期先のPCにも届く」ことを表示する。共有設定を書き戻すため、既存と同じ確認を残す。
2. 確認後にsettings.jsonの内容・存在状態・revisionを再照合する。正常な設定が届いていたら、その設定を採用して復元を中止する。
3. 読み取り不能、通常ファイルでない、4MiB超など、現ファイルを安全に退避できない場合は上書きしない。保存先と手動退避の案内を出す。
4. 現在の破損bytesをPC専用の `invalid-<時刻>-<UUID>.txt` へ退避する。元ファイルが存在しなければ退避は不要。退避失敗時は復元しない。
5. 候補を原子的にsettings.jsonへ保存する。確認・退避後に外部更新を検出した場合は停止して再評価する。
6. 保存が成功してからStoreとバックアップ状態を更新し、既存のchanged経路で反映する。設定エラー通知を解消し、起動時適用値と異なる項目があれば再起動待ち通知へ移る。

正常候補のファイル、退避した破損bytes、既存の正常世代は復元操作で削除しない。既存の正常世代の保持上限は維持する。

復元と任意の外部同期プログラムを完全に排他にはできない。復元中の再照合と失敗時の中止で検出可能な競合を防ぎ、直後に正常な外部設定が届いた場合は通常の受信方針で採用する。

### 8.2 正常なバックアップがない場合

通知基盤の初期化前に設定読込が失敗するため、この場合だけ起動時のネイティブdialogを使う。復旧のために仮の設定でAppletや外部接続を起動しない。

dialogに「正常なJSONから復元」「保存先を開く」「再読み込み」「終了」を用意する。

- 「正常なJSONから復元」はネイティブファイル選択で選ばれたJSONを4MiB以下・構文・設定schemaで検証し、8.1と同じ退避・外部更新照合・原子的保存を行う。同期先にも反映する確認を行い、選択元ファイルは変更しない。
- 「保存先を開く」で、別PCの正常ファイルを戻す、同期の到着を待つ、JSONを手動修正する方法を案内する。
- 「再読み込み」はファイルを検証する。修復されていれば、復旧用プロセスを通常の起動経路へ再起動させ、ハードウェアアクセラレーションをapp.ready前に適用し直す。初期化済みのElectronへ設定だけ差し込んで起動済み扱いにはしない。
- 読み込みが失敗する間はdialogを維持し、エラー理由を更新する。自動再起動ループを作らない。

共有ファイルを空の設定で上書きする自動初期化や、復元できない項目を推測して削除する修復は行わない。ファイルも履歴も存在しない通常の初回起動は、既存の初期設定生成を維持する。

復旧dialog内の再読込では通常初回起動の自動生成を呼ばず、読み取り専用の検証を使う。復旧の途中でファイルが一時的に消えても、空の設定を生成しない。起動時dialogも安全なエラー分類を表示し、生のJSONや例外全文を転載しない。

## 9. 実装構成

| 構成 | 責務 |
| --- | --- |
| SettingsStore | 読込・保存・正常バックアップ・復元。障害分類と状態遷移を通知用に提供する |
| 設定保存の共通経路 | Windows登録などStoreの外で失敗する保存処理を分類し、成功/失敗の処理世代を報告する |
| 既存の設定適用経路 | 即時反映の成功・失敗を対象機能とrevisionに対応付けて報告する |
| SettingsHealthNotificationSource（追加予定） | 起動時適用値との差分、設定障害、復旧操作可否を評価し、TypedNotificationsへ投影する |
| 共通の設定復旧処理 | 既存IPC・通知action・起動時dialogから同じ検証・退避・復元処理を呼ぶ |
| TypedNotifications / NotificationService | 種類別方針、dedupe、action排他、表示先、履歴を担当する |
| 起動時復旧dialog | 通知基盤を起動できない場合だけ、正常JSONの選択と再読込を提供する |

通知発行元は正常に保存された値と障害情報だけを読み、設定の下書きや画像bytesを持たない。分類用の追加情報は内部状態とし、既存の公開snapshot/schemaへは必要性を確認せず増やさない。

一般設定には安全な状態要約・復旧可否を `SettingsPageAuxiliary` の任意フィールドとして投影し、復旧操作は既存の不透明なaction IDで公開する。内部の障害履歴や全設定を追加Shellへ渡さず、Default Shellと追加Shellで同じ操作契約を使う。既存の復元IPCも同じ本体処理へ接続して互換性を保つ。

`syncError` の現在の文字列はバックアップ失敗と受信失敗が混在しているため、文字列一致だけで分岐しない。既存画面向けの要約との互換性を保ちながら、内部の原因と復旧可否を分離する。

受信した設定の妥当性と、バックアップの保存結果も分離する。正常な受信値を採用できた場合、バックアップ保存の失敗をJSON不正として扱わず `backup-failed` を残す。既存の `accept` にあるバックアップ先行処理を見直し、バックアップ失敗だけで正常な外部設定の採用が止まらないようにする。

通知サービスが準備できる前の障害は内部状態に保持し、startupReady後に評価する。起動に必要な正常設定を確保できない場合だけ8.2へ分岐する。通知発行失敗はログへ記録し、成功済みの設定保存を失敗に戻したり通知エラーを再帰通知したりしない。

## 10. 実装の順序と確認項目

1. 読込・保存・バックアップの障害分類と解消条件を整理する。通常の入力検証・revision保護は維持する。
2. 本体の通知2種類と、起動時適用値を比較する発行元を追加する。
3. 既存の再起動経路へactionを接続し、同時保存・多重押下・終了処理を検証する。
4. バックアップ復元を共通化して通知から接続する。起動時dialogと正常JSONからの復元を追加する。
5. 関連する単体・GUI・固定EXE試験を行い、実装差分をレビューしてから版更新とpublishを行う。文書だけの現在の段階では行わない。

| 検証 | 期待結果 |
| --- | --- |
| UI/API/外部ファイルからGPU設定を変更 | 同じ再起動待ち判定、理由とボタンを表示 |
| GPU設定を起動値へ戻す | 再起動せず通知が終了 |
| 別項目や同じ内容を連続更新 | 通知が増殖せず、focusを奪わない |
| 再起動ボタン、多重押下、別表示先からの押下 | 1回だけ再起動。元EXE/profile/画面を復元 |
| 入力途中・保存失敗値を残して再起動 | 勝手に保存せず、保存済み値で起動 |
| 一時的ロック/削除とその後の復旧 | 最後の正常値を維持。短い障害で通知を出さない |
| 継続する不正JSON・欠落・バックアップ失敗 | 原因を区別して通知し、対応する成功だけで解除 |
| 正常な受信とバックアップ失敗の同時発生 | 受信値は採用し、バックアップ障害だけを残す |
| 設定適用の失敗・後続の成功・古い非同期応答 | 保存と反映の成否を区別し、古い結果で解消済み障害を再発させない |
| 入力検証失敗・revision競合・UACキャンセル | 従来の画面内説明。不要な再起動通知なし |
| 通知設定のOFF/ON、表示先変更 | 同episodeの再送なし、表示先変更でIDを保持、読み上げ既定OFF |
| 通知をOFFにした状態で復旧 | 一般設定の状態表示と復元操作を利用でき、全体バナーは重複しない |
| 設定エラーと再起動待ちが同時発生 | 種類ごとに1件。双方に理由と再起動操作 |
| 破損JSONで起動、正常バックアップあり | バックアップで動作、共有ファイルは未変更、復元導線あり |
| バックアップ復元、途中キャンセル | 成功時だけ保存・状態更新。キャンセルでファイル変更なし |
| 復元確認中に正常な外部設定が到着 | 復元を中止し、受信した正常設定を採用 |
| 退避不可・4MiB超・保存不可 | 破損ファイルと候補を保持し、上書きしない |
| バックアップなしの起動失敗 | 復旧dialogから修正/正常JSONの選択/再読込が可能 |
| 不正な復元候補、候補選択の取消 | 現ファイルと候補を変更しない |
| 起動時復旧後に再起動 | 起動前設定を反映し、同一profileで通常起動。ループしない |
| 履歴と再起動後の状態 | 生JSON・秘密値・操作関数を保存せず、現状だけを再通知 |

既存の `tests/settings-sync.test.cjs`、`tests/settings-editing.test.cjs`、`tests/notification-policy.test.cjs`、`tests/notification-foundation.test.cjs` と、設定同期・ハードウェアアクセラレーション・通知のGUI試験を関連回帰とする。追加する発行元と復旧処理には状態遷移・競合・失敗を確かめる試験を用意する。

発行後は固定した単一EXEを隔離profileで動かし、通知の実ボタン、実再起動、破損からの復元を確認する。実際の同期サービスによる配送、UAC承認、物理クリックは試験条件と確認結果を分けて記録する。

## 11. 保存・互換性・文書の更新

設定の3方向マージやbase保存、同期サービス、追加の共有履歴ファイルは導入しない。復旧は既存バックアップと破損bytesの退避方式を使う。既存IPCと保存済みSettingsの互換性を維持し、新しい通知種類は既存のnotificationPreferences.overridesで設定できる。

実装時は通知種類に対応する設定項目の追加として、[版更新の判断](development-workflow.md#版更新の判断)に従い本体のマイナー版を更新する。実装開始時の最新版本を基準とし、この設計書で番号を固定しない。

実装後に本書の状態を更新し、現行の通知・設定同期文書に必要な契約を反映する。READMEには再起動通知と復旧の利用方法、VERIFICATIONには実施した試験と未確認事項を記録する。設計しただけの動作を現行機能として記載しない。
