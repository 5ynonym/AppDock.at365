状態: mainに実装済み。現行仕様は[設定同期](settings-sync.md)、実行結果と実機確認の範囲は[検証記録](../VERIFICATION.md)を参照する。第2節の表は実装前との差分を示す。

現行契約は[設定同期](settings-sync.md)、[設定基盤](settings-foundation.md)、[通知基盤](notifications.md)、[共通のエラー通知とログ](error-reporting.md)、[Windows起動設定](launch-settings.md)を参照する。この文書は採用した方針、実装構成、確認すべき条件をまとめる。検証表は確認観点であり、全項目の実機確認済みを意味しない。

## 1. 要求と採用方針

- EXE隣の `settings.json` に同期で届いた正常な設定を採用する。別PCの変更と、このPCの変更を保存して自動統合する3方向マージは導入しない。
- AppDockからの妥当な変更は即時保存する。外部更新は読み直して実行中のAppDockへ適用する。
- 設定の変更を反映するために再起動が必要な場合、理由を通知基盤へ表示する。
- 設定の読み込み・保存などで処理上のエラーが起きた場合も、理由と必要な対処を示して再起動を案内する。再起動だけで直るとは断定しない。
- 両方の通知に「再起動」ボタンを置く。自動では再起動しない。
- JSONが壊れた場合に、正常なバックアップから復元できるようにする。壊れた内容は復元前にPC内へ退避する。
- 同じ問題で通知を増殖させず、問題が解消したら終了する。通知のために共有ドラフト・dirty・全体保存/破棄を復活させない。

本設計の「設定エラー」は保存先・受信ファイル・バックアップ・設定保存処理の障害を指す。編集中の不完全な数値やJSON、入力値の検証違反、古いrevisionの拒否は、現在の入力欄で説明する。通常の入力修正まで再起動通知の対象にはしない。

## 3. settings.jsonを優先する範囲

### 3.1 外部ファイルの取り込み

1. 安定した内容を読み取り、JSON構文と設定schemaを検証する。
2. 正常なら保存済み設定をその内容へ更新する。このPCの以前の設定との差分を保存して戻さない。
3. 既存のchanged経路へ通知し、即時反映できる項目を適用する。
4. 再起動待ちと設定障害の状態を再評価する。

正常な受信だけを理由にファイルを整形・書き戻ししない。同じ内容の受信や自分の保存を再検出しても、通知を再発行しない。

保存直前に未反映の外部更新を検出した場合は、現在どおり外部ファイルを採用して古い保存要求を拒否する。画面内の不完全入力・競合表示の保持方針は[設定基盤](settings-foundation.md)に従う。入力を黙って破棄するUI変更は本設計に含めない。

ファイルの優先は「同期サービスがこのPCのsettings.jsonへ置いた内容を採用する」という意味であり、編集日時が一番新しい版の判定ではない。別名の同期競合コピーの自動取込、PC間の変更履歴、同期サービスの設定変更は行わない。

### 3.2 不正・欠落・一時的ロック

不正なファイルを設定値として採用せず、最後の正常値で動作を継続する。自動で初期値を書き戻したり、破損ファイルを削除したりしない。

監視による一時的な失敗は内部の障害状態へ記録し、2秒継続した場合に共通エラー報告へ接続する。短時間で正常に戻れば通知・共通エラーログを発行しない。保存要求の確定した失敗と、起動時に判明したバックアップ継続状態は待機せず通知対象にする。

直接の再読込・保存・復元で正常な状態を確認した場合も、監視側のエラー重複抑止を解除する。正常期間をpollが観測できなかった場合でも、その後に同じ読込障害が再発すれば新しい障害として検出する。

通常保存の原子的置換とrevision保護は維持する。これらを、任意の外部プロセスとの完全な排他やPC間の同時書き込み保証とは扱わない。

## 4. 再起動が必要な設定の判定

### 4.1 最初に対象とする設定

`host.hardwareAcceleration` を対象とする。Electronへ起動前に適用した設定値を、このプロセスの基準値として保持する。現在の保存済み値がその基準値と異なる間だけ再起動待ちにする。

実行環境のGPU対応可否や描画のフォールバックを「設定変更」と誤認しないため、判定基準は起動時に要求した値とする。実際のGPU状態は検証で別途確認する。

| 変化 | 動作 |
| --- | --- |
| 起動値と同じ | 通知なし |
| 画面/API/外部ファイルから異なる値へ変更 | 理由付き通知を開始 |
| 再起動前に起動値へ戻す | 通知をresolvedにする |
| 再起動して保存済み値を適用 | 新プロセスでは通知なし |
| 無関係な設定だけ変更 | 通知ID・状態を維持 |

起動時の基準値は3方向マージのbaseではなく、再起動待ち判定に必要なメモリー内の値だけである。追加のbaseファイルを作らない。

### 4.2 次回起動方針との区別

`startMinimized`、更新の起動時確認、Appletの起動遅延などは次の起動時の動作を指定する設定であり、変更だけで現在のプロセスを再起動必須にはしない。Applet設定は既存のsettingsChanged契約を使い、宣言のない項目を本体が勝手に再起動対象へ分類しない。

`runAsAdministrator` も次回起動方針として既存仕様を維持する。管理者起動の失敗は設定エラーの説明対象になり得るが、一般の再起動ボタンに自動的な昇格・降格を追加しない。「管理者として再起動」は既存の専用操作を使う。管理者プロセスの通常再起動は権限を引き継ぐため、OFFへの変更については「完全終了して通常権限で起動」を案内する。

外部JSONで `startAtLogon` が変わってもWindowsのタスク登録を自動で変更しない。再起動で登録まで完了すると案内しない。

将来、ほかに実行中へ適用できない設定を追加した場合は、理由・起動時適用値・解消条件を登録する。本体の設定全体を比較して再起動通知を出す方式にはしない。

## 5. 設定エラーの分類と解消条件

`SettingsHealth`は障害元のkeyごとに種別、安全な説明、発生時刻、即時報告の可否を保持する。keyごとの処理世代は別に保持し、古い成功・失敗を拒否する。ホストの同期反映には保存済みrevision、非同期のキー登録・Applet構成反映には処理ごとに増加する世代を使う。設定値や途中入力そのものは保持せず、表示文字列だけで障害を判定しない。

| 種別 | 通知に示す理由と対処 | 解消条件 |
| --- | --- | --- |
| `read-invalid` | JSON構文/schemaが不正。修正・復元が必要で、再起動だけでは修復されないことを表示。最後の正常値での継続は一般設定にも表示 | 正常な受信または復元完了 |
| `read-unavailable` | ファイルの欠落・読み取り権限・継続するロック。保存先を確認して再起動 | 正常な読込 |
| `save-failed` | 設定保存を完了できなかった。変更が保存されたとは表示しない。保存先を確認し再起動後に再設定 | 同じ保存系統の後続処理成功、または再起動後の再評価 |
| `backup-failed` | PC内の正常バックアップまたは復元前の破損bytesの退避に失敗。空き容量・権限の確認を案内。通常のバックアップ更新失敗だけでは正常な受信・保存を取り消さない | 実際のバックアップ保存成功 |
| `apply-failed` | 設定は保存/受信できたが、関連するホスト機能への反映を完了できない。対象機能と理由を示し、再起動を案内 | 対象機能で現在の設定の反映成功 |
| `launch-save-failed` | Windows起動設定の変更・復元処理で障害。登録状態を確認して再起動 | 再確認と必要な保存処理の成功 |

UACの明示キャンセル、入力検証、revision競合、操作中のBUSYは処理障害と分け、操作元の説明を維持する。設定と無関係なAppletの異常終了や通信障害をこの通知へ混ぜない。

同時に複数の設定障害がある場合は、共通「エラー通知」のうち設定を発行元とする1件に集約し、未解消の理由を列挙する。AI等の別処理の失敗は集約・解除しない。一つの正常受信で保存失敗やバックアップ失敗まで一括解除しない。非同期処理の古い失敗結果が新しい成功を上書きしないよう、処理世代を照合する。

反映失敗は既存の各機能が返す設定適用結果を使い、対象機能と処理世代を対応付ける。たとえばショートカットのOS登録失敗を、保存失敗や正常な一時登録解除と混同しない。機能別の詳細表示は維持し、無関係な実行エラーをまとめて設定障害へ変換しない。

OS例外・JSON本文・APIキー・URLなどを通知本文や履歴へそのまま転記しない。原因は処理段階と既知のエラー分類から安全な文言へ変換する。詳細ログの既存方針も維持する。

## 6. 通知の種類・表示・寿命

`notificationCatalog` に追加する本体通知種類は再起動待ちだけとする。設定エラーはErrorReporterから既存の共通「エラー通知」へ接続し、設定専用のエラー種類を増やさない。設定ページへの項目追加は既存カタログからの生成を使う。

| 項目 | 再起動待ち | 設定エラー（既存の共通種類を使用） |
| --- | --- | --- |
| ownerKind / ownerId | `host` / `settings` | `host` / `errors` |
| typeId | `restart-required` | `operation-failed` |
| 設定上の名前 | 設定の反映に再起動が必要 | エラー通知 |
| レベル | warning | error。バックアップ・退避失敗は共有ファイルの読込/保存失敗と区別して説明 |
| 既定表示先 | banner | banner / desktop |
| 許可する表示先 | banner / desktop / windows | banner / desktop / windows |
| 必須表示先（requiredTargets） | なし | banner。有効な間は解除・通知センターのみを不可とする |
| 寿命 | condition | userDuration。初期10秒、利用者の表示時間/manual設定に従う |
| 通知全体のOFF | 設定なし | 設定なし。エラーログにも記録する |
| 履歴 | persistent、安全な要約だけ | persistent、安全な要約だけ |
| 読み上げ | 既定OFF | 既定OFF |

表示先・表示時間・読み上げは既存の種類別設定を使用する。新しい専用設定ファイルは作らない。必須表示先は[通知種類の制約](notifications.md#通知種類の制約)に従って登録する。

再起動待ちはconditionのため時間経過や閉じる操作では解消しない。設定エラーの通知は共通の表示期限・閉じる操作に従うが、それで設定障害が解消したとは扱わない。期限切れ・閉じる操作の後も、一般設定の状態表示と復旧操作を維持する。同じ障害の通知を繰り返して表示時間の設定を迂回しない。

現在のホスト全体の `syncError` バナーは通知へ統合し、同じ障害を二重に表示しない。一般設定に「設定ファイル」の状態と復旧操作を置き、通知を無効にした場合も確認・復元できるようにする。保存先の詳細や復旧操作はここに集約し、入力欄固有の検証エラーはその欄に残す。

表示例:

```text
再起動が必要です
ハードウェアアクセラレーションの変更を反映するには、AppDockの再起動が必要です。
[再起動] [保存先を開く]
```

```text
設定を確認して再起動してください
settings.jsonの形式が不正です。ファイルを修正するか、正常な設定から復元してください。再起動だけでは修復されません。
エラーコード: read-invalid
[再起動] [バックアップで復元] [保存先を開く]
```

設定エラーのタイトルは、再起動の案内と修正の必要性を両方示す。「再起動すれば必ず修復される」という表現は使わない。設定障害がすべて解消した場合は、再起動を強制せず、対応する通知がactiveなら終了する。

### 6.1 重複と状態遷移

- 再起動待ちと設定障害で発行元・用途を区別し、episodeごとの安定した識別子で同じactive通知を更新する。共通エラー種類全体を一つのdedupeKeyにまとめない。
- 理由・操作可否に変化がなければ報告しない。poll、画面更新、既読変更だけでは再発行・再記録しない。新たな設定障害の発生・原因変更は安全なログへ記録し、通知が既に終了していればそのepisodeでは再表示しない。
- 条件が解消したら対応するactive通知をresolvedにする。すでに期限切れ・閉じた通知は再発行しない。設定障害がすべて解消した後に再発した場合は新しいepisodeとして新IDを発行する。
- 通知全体のOFF設定は設けない。旧OFF値は読込時に破棄し、設定の変更だけで同じepisodeを再送しない。
- 表示先変更はTypedNotificationsの既存reconcileを使い、通知IDを保つ。
- 再起動後は旧active履歴を既存どおりinterruptedにする。現在の設定とエラーを再評価して、なお問題がある場合だけ新規通知を発行する。
- 終了時は発行元を先に停止し、購読・遅延タイマー・操作を解放する。通知サービスの終了後に発行しない。

設定障害の更新・解消は`ErrorReporter.episode()`の`update` / `resolve`で扱う。`TypedNotifications.isActive()`で実際の通知状態を確認し、終了済みの通知を再生成しない。通知原因とactionのkey・label・primary・disabledが同じなら、通知revisionも更新しない。

## 7. 再起動ボタン

本体が発行する通知actionとして `key: restart`、`label: 再起動` を設定する。rendererへ任意コマンドや関数を渡さず、既存の通知action ID、revision、requestId検査を使う。

処理は現在の `appdock.restart` / `quitHost(true)` と同じ経路を使い、元の単一EXE、profile、`--restore-view`、終了時のApplet停止を保持する。通知からの再起動のために、途中の入力や保存失敗値を強制保存しない。

非同期のWindows起動設定保存・復元確認トランザクション中はボタンをdisabledにし、再起動処理自身も拒否する。通常のSettingsStore保存は同期処理であり、その途中に再起動actionは割り込まない。基盤の通知単位の操作排他に加え、ホスト全体の終了状態で多重再起動を防ぐ。別通知から押された場合も起動プロセスは増やさない。

保存先の修正が必要な場合でも再起動ボタンは用意し、本文で前提条件を伝える。ボタン押下だけでエラーをresolvedにせず、終了・新プロセスの状態に従う。`app.relaunch`の呼び出しが例外になった場合は終了状態へ移らず、既存の通知actionのエラー表示を使う。終了後の新プロセス起動の成功を保証する追加監視は行わない。

バナー・独立デスクトップ・通知センターにはボタンを表示する。Windows通知は既存契約に合わせ、クリックで通知センターを開き、そこで「再起動」を押す。OS通知のクリックだけで再起動しない。Windows固有のボタン追加はこの設計に含めない。

## 8. JSON破損からの復旧

### 8.1 正常なバックアップがある場合

既存のPC専用 `settings-backups/last-good.json` と直近20世代を使う。起動時は候補を再検証し、最新の読み取り可能な正常設定で動作を続ける。実行中の破損では最後の正常値を保持する。共有ファイルは自動では修復せず、設定エラー通知に「バックアップで復元」を表示する。

復元ボタンは本体の共通復元処理へ接続し、既存IPCと通知で別実装にしない。最新の正常候補を使用し、過去世代の選択UIは設けない。読込障害を表す `recovered` と、再検証した正常候補の存在を両方確認する。保存・バックアップ・反映だけの障害には、正常な共有ファイルを巻き戻す復元操作を表示しない。

復元手順:

1. 復元する候補を再読込・検証し、確認画面にバックアップ日時と「同期先のPCにも届く」ことを表示する。共有設定を書き戻すため、既存と同じ確認を残す。
2. 確認後にsettings.jsonの内容・存在状態・revisionを再照合する。正常な設定が届いていたら、その設定を採用して復元を中止する。
3. 読み取り不能、通常ファイルでない、4MiB超など、現ファイルを安全に退避できない場合は上書きしない。保存先と手動退避の案内を出す。
4. 現在の破損bytesをPC専用の `invalid-<時刻>-<UUID>.txt` へ退避する。元ファイルが存在しなければ退避は不要。退避失敗時は復元しない。
5. 候補を原子的にsettings.jsonへ保存する。確認・退避後に外部更新を検出した場合は停止して再評価する。
6. 保存が成功してからStoreとバックアップ状態を更新し、既存のchanged経路で反映する。原因ごとの解消条件を評価し、設定障害がすべて解消したら対応するactive通知を終了する。バックアップや反映の失敗が残る場合は維持する。起動時適用値と異なる項目があれば再起動待ち通知を開始する。

正常候補のファイル、退避した破損bytes、既存の正常世代は復元操作で削除しない。既存の正常世代の保持上限は維持する。

復元と任意の外部同期プログラムを完全に排他にはできない。復元中の再照合と失敗時の中止で検出可能な競合を防ぎ、直後に正常な外部設定が届いた場合は通常の受信方針で採用する。

### 8.2 正常なバックアップがない場合

通知基盤の初期化前に設定読込が失敗するため、この場合だけ起動時のネイティブdialogを使う。復旧のために仮の設定でAppletや外部接続を起動しない。

dialogに「正常なJSONから復元」「保存先を開く」「再読み込み」「終了」を用意する。

- 「正常なJSONから復元」はネイティブファイル選択で選ばれたJSONを4MiB以下・構文・設定schemaで検証し、8.1と同じ退避・外部更新照合・原子的保存を行う。同期先にも反映する確認を行い、選択元ファイルは変更しない。
- 「保存先を開く」で、別PCの正常ファイルを戻す、同期の到着を待つ、JSONを手動修正する方法を案内する。
- 「再読み込み」はファイルを検証する。修復されていれば、復旧用プロセスを通常の起動経路へ再起動させ、ハードウェアアクセラレーションをapp.ready前に適用し直す。初期化済みのElectronへ設定だけ差し込んで起動済み扱いにはしない。
- 読み込みが失敗する間はdialogを維持し、エラー理由を更新する。自動再起動ループを作らない。

共有ファイルを空の設定で上書きする自動初期化や、復元できない項目を推測して削除する修復は行わない。ファイルも履歴も存在しない通常の初回起動は、既存の初期設定生成を維持する。

復旧dialog内の再読込では通常初回起動の自動生成を呼ばず、読み取り専用の検証を使う。復旧の途中でファイルが一時的に消えても、空の設定を生成しない。起動時dialogも安全なエラー分類を表示し、生のJSONや例外全文を転載しない。

## 9. 実装構成

| 構成 | 責務 |
| --- | --- |
| SettingsStore | 読込・保存・正常バックアップ・復元。障害分類と状態遷移を通知用に提供する |
| SettingsHealth | 原因別の障害状態と処理世代。通知寿命と独立して正常化を判定する |
| 設定保存の共通経路 | Windows登録などStoreの外で失敗する保存処理を分類し、保存・再確認の成功と失敗を報告する |
| 既存の設定適用経路 | 即時反映の成功・失敗を対象機能と処理世代に対応付けて報告する |
| SettingsHealthNotifications | 起動時適用値との差分、設定障害、復旧操作可否を評価する。再起動待ちはTypedNotifications、設定障害はErrorReporterへ接続し、episodeを管理する |
| ErrorReporter | 共通エラー種類と安全なログを維持し、本体の復旧action・設定障害episodeに対応する通知の更新/解消を扱う |
| SettingsStore.prepareRecovery / restoreRecovery | 既存IPC・通知action・起動時dialogから同じ検証・退避・復元処理を呼ぶ |
| TypedNotifications / NotificationService | 種類別方針、dedupe、action排他、表示先、履歴を担当する |
| recoverSettingsAtStartup / SettingsRecoveryUi | 通知基盤を起動できない場合だけ、ネイティブdialogで正常JSONの選択と再読込を提供する |

通知発行元は正常に保存された値と障害情報だけを読み、設定の下書きや画像bytesを持たない。分類用の追加情報は内部状態とし、既存の公開snapshot/schemaへは必要性を確認せず増やさない。

ErrorReporterの`episode`は本体内部の契約とする。ホストが検証したactionだけを受け付け、発行元・episodeに対応する通知だけを更新/終了する。単発`report`を使うAIの重複抑止・共通ログ・秘密値の排除を維持する。通知寿命や必須表示先を設定処理側で上書きせず、共通の種類別設定に従う。MCP・Appletへ任意の本体エラー発行APIを追加するものではない。

一般設定には安全な状態要約・復旧可否を `SettingsPageAuxiliary` の任意フィールドとして投影し、復旧操作は既存の不透明なaction IDで公開する。内部の障害履歴や全設定を追加Shellへ渡さず、Default Shellと追加Shellで同じ操作契約を使う。既存の復元IPCも同じ本体処理へ接続して互換性を保つ。

`syncError`は`SettingsHealth`の安全な説明を連結する互換用getterとし、文字列一致で分岐しない。一般設定へは`SettingsPageAuxiliary.settingsHealth`で再起動理由、障害説明、正常値での継続、復元可否、処理中状態だけを投影する。

受信した設定の妥当性と、バックアップの保存結果も分離する。`accept`は正常な受信値を採用し、`tryBackup`が失敗した場合は `backup-failed` を残す。バックアップ失敗をJSON不正として扱わず、正常な外部設定の採用を止めない。

通知サービスが準備できる前の障害は内部状態に保持し、startupReady後に評価する。起動に必要な正常設定を確保できない場合だけ8.2へ分岐する。共通エラー報告は元の障害を通知より先にログへ記録する。通知処理の例外を設定操作へ伝播させず、成功済みの設定保存を失敗に戻したり通知エラーを再帰通知したりしない。

## 10. 検証の観点と範囲

以下は設計上の確認観点と期待結果。実行した試験、fixtureで代替した条件、未確認事項は[検証記録](../VERIFICATION.md)に記録し、この表から実機での成功を推定しない。

| 検証 | 期待結果 |
| --- | --- |
| UI/API/外部ファイルからGPU設定を変更 | 同じ再起動待ち判定、理由とボタンを表示 |
| GPU設定を起動値へ戻す | 再起動せず通知が終了 |
| 別項目や同じ内容を連続更新 | 通知が増殖せず、focusを奪わない |
| 再起動ボタン、多重押下、別表示先からの押下 | 1回だけ再起動。元EXE/profile/画面を復元 |
| 入力途中・保存失敗値を残して再起動 | 勝手に保存せず、保存済み値で起動 |
| 一時的ロック/削除とその後の復旧 | 最後の正常値を維持。短い障害で通知を出さない |
| 継続する不正JSON・欠落・バックアップ失敗 | 原因を区別して通知し、対応する成功だけで解除 |
| 正常な受信とバックアップ失敗の同時発生 | 受信値は採用し、バックアップ障害だけを残す |
| 設定適用の失敗・後続の成功・古い非同期応答 | 保存と反映の成否を区別し、古い結果で解消済み障害を再発させない |
| 入力検証失敗・revision競合・UACキャンセル | 従来の画面内説明。不要な再起動通知なし |
| 通知の表示先変更 | 同episodeの再送なし、表示先変更でIDを保持、読み上げ既定OFF |
| 共通エラーの必須バナーと旧OFF値 | バナー解除・センターのみを拒否。旧OFF値は無視し、通知とログへ残す |
| 共通エラーの期限切れ・閉じる操作 | 通知は終了し、未解消の状態と復旧操作は一般設定に残る。同episodeを再表示しない |
| 通知を閉じた状態で復旧 | 一般設定の状態表示と復元操作を利用でき、全体バナーは重複しない |
| 設定エラーと再起動待ちが同時発生 | 設定を発行元とするエラー1件と再起動待ち1件。双方に理由と再起動操作 |
| AIの失敗と設定障害が同時発生・設定だけ復旧 | 別の失敗として報告。設定側の更新・解消でAIの通知やログを変更しない |
| 破損JSONで起動、正常バックアップあり | バックアップで動作、共有ファイルは未変更、復元導線あり |
| バックアップ復元、途中キャンセル | 成功時だけ保存・状態更新。キャンセルでファイル変更なし |
| 復元確認中に正常な外部設定が到着 | 復元を中止し、受信した正常設定を採用 |
| 退避不可・4MiB超・保存不可 | 破損ファイルと候補を保持し、上書きしない |
| バックアップなしの起動失敗 | 復旧dialogから修正/正常JSONの選択/再読込が可能 |
| 不正な復元候補、候補選択の取消 | 現ファイルと候補を変更しない |
| 起動時復旧後に再起動 | 起動前設定を反映し、同一profileで通常起動。ループしない |
| 履歴と再起動後の状態 | 生JSON・秘密値・操作関数を保存せず、現状だけを再通知 |

既存の `tests/settings-sync.test.cjs`、`tests/settings-editing.test.cjs`、`tests/notification-policy.test.cjs`、`tests/notification-foundation.test.cjs`、`tests/error-reporter.test.cjs`、`tests/ai.test.cjs`、`tests/windows-launch.test.cjs` 等を関連回帰とする。追加した `tests/settings-recovery.test.cjs` と `tests/settings-health-notifications.test.cjs` は状態遷移・競合・失敗、起動復旧loopを検証する。

`scripts/settings-recovery-ui-test.cjs`はソースまたは固定した単一EXEを隔離profileで動かし、通知の実ボタン、実再起動、破損からの復元を確認する。ネイティブ確認dialogの回答はfixtureで与える。実際の同期サービスによる配送、UAC承認、物理クリックは試験条件と確認結果を分けて記録する。

## 11. 保存・互換性・文書の更新

設定の3方向マージやbase保存、同期サービス、追加の共有履歴ファイルは導入しない。復旧は既存バックアップと破損bytesの退避方式を使う。既存IPCと保存済みSettingsの互換性を維持し、新しい再起動待ちの通知種類は既存のnotificationPreferences.overridesで設定できる。設定エラーは共通「エラー通知」の設定をそのまま使い、専用の設定項目は作らない。

通知種類に対応する設定項目の追加として、[版更新の判断](development-workflow.md#版更新の判断)に従い本体のマイナー版を更新した。版と配布物の照合は[検証記録](../VERIFICATION.md)へ記録する。

現行の通知・設定同期文書に操作と保存の契約を反映し、READMEには再起動通知と復旧の利用方法を記載する。本書は設計判断と実装構成、VERIFICATIONは実施した試験と未確認事項を担当する。
