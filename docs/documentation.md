# ドキュメント方針

READMEはアプリを使う人の入口です。AppDockと各Applet、および今後作成するリポジトリでも、利用情報と開発情報を分けます。

| 文書 | 読者と内容 |
| --- | --- |
| `README.md` | 利用者。概要、動作環境、必要なホスト版、配布物の導入・更新、操作、設定、保存先、制約、困ったときの対処 |
| `DEVELOPMENT.md` | 開発者。開発環境、依存ソース、ビルド、テスト、発行、開発者用の配置スクリプト、実装の補足、詳細文書への入口 |
| `docs/` 内の開発文書 | SDK・API・内部構造・移行設計など、長くなる専門情報。既存文書を正本としてリンクする |
| `VERIFICATION.md` | 実行した検証、その条件と結果、成果物の版・ハッシュ、未確認事項。手順そのものは開発文書を参照する |

## 切り分けの判断

- 配布済みのアプリを使うために必要な説明はREADMEに置きます。ファイル配置や更新の注意は、ビルド手順と同じ章にあってもREADMEに残します。
- `publish.bat`や`deploy.bat`など、ソースリポジトリから成果物を生成・配置する操作はDEVELOPMENTに置きます。通常の利用者へSDKや開発ツールの導入を要求しません。
- 利用PCに必要なRuntimeはREADME、開発に必要なSDKはDEVELOPMENTに記載します。Appletの最低ホスト版はmanifestと照合します。
- 設定JSON、コマンドID、互換性、保存先は利用者が手動設定や移行に使う範囲でREADMEに残します。実装クラス、通信方式、Windows APIの選定理由は開発文書へ移します。
- 過去の実装報告はREADMEの操作説明に混ぜません。現行の機能別に整理し、履歴が必要なら日付・版を付けて開発文書や検証記録へ残します。
- README末尾に開発ガイドへの1つの短いリンクを置きます。開発ガイドからREADME、VERIFICATION、必要な詳細文書へリンクします。

## 新規リポジトリの最小構成

```text
README.md
DEVELOPMENT.md
VERIFICATION.md       検証を実施した時点で記録
docs/                 詳細文書が必要な場合
```

READMEの基本順序は「概要 → 動作環境 → 導入・更新 → 使い方 → 設定 → 保存先・制約」です。小さいアプリでは章をまとめても構いません。DEVELOPMENTは「必要な環境 → ビルド → テスト → 発行・配置 → 実装・詳細文書」を基本にします。未確認の機能や存在しない配布先をテンプレートから書き足さないでください。

## 更新時の確認

1. 既存の変更を保持し、移動した手順・注意事項の欠落や重複がないか確認する。
2. 文書の場所が変わる場合は、相対リンクと他の文書からの参照を更新する。
3. READMEの設定例やコードブロックを読む既存テストがないか確認する。利用者用の例は原則READMEに残す。
4. ローカルリンク、Markdownの構造、`git diff --check`を確認する。設定例を変更した場合は関連する既存テストも実行する。
5. 文書のみの整理を、ビルド・実機動作・配置の検証済みと扱わない。実施した確認だけを報告する。

AppDockの開発文書全体への入口は[DEVELOPMENT.md](../DEVELOPMENT.md)です。
