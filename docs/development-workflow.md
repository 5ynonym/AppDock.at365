# 実装・コミット・リリースの共通手順

AppDock本体と各Appletに適用します。各repoのAGENTS/DEVELOPMENTにある試験コマンドと機能別の確認項目は、必要な検証を選ぶための一覧です。毎回全項目を実行する指定ではありません。実行段階と検証結果の再利用は、この手順を正本とします。

## 一連の作業完了時の音声通知

依頼された工程と必要な検証・記録・後片付けをすべて終えたら、最終回答の直前に[共通の音声通知手順](../../AGENTS.md#一連の作業完了時の音声通知)に従い、AppDock MCPで1回だけ通知します。本文はそのときの作業内容と結果を短く要約し、普段の会話と同じ口調で伝えます。実装からコミット・リリースまで同じ依頼で続ける場合は、最後の工程が終わってから通知します。ボイス・速度は既定値を使い、再生完了は待ちません。AppDockが利用できない場合は省略し、通常の最終回答へ進みます。

## 実装

1. 変更範囲と影響先を確認し、機能と必要なテストを実装します。既存回帰を毎回一律には実行せず、変更の危険度や不確実性に応じて必要なものを選びます。保存形式、認証、共通API、更新・復旧、入力フックなどの変更では、関連回帰を実装中に実行して構いません。
2. 対象のビルド・型検査と変更部分の動作を確認します。実行時点から[検証証跡](#検証証跡)を残し、後のコミットで結果を再利用できるようにします。証跡を作るために不要な試験を追加せず、既存の適切な試験を優先します。失敗・未確認を成功扱いしません。
3. 動作確認用の発行前に、実装差分と影響先を1回レビューします。要件との一致、既存動作への影響、設定・保存ファイル・公開APIの変更、必要な検証の不足を確認します。下記の版更新区分も判定し、レビューをコミット依頼時まで先送りしません。
4. 修正が必要な指摘へ対応し、修正差分と影響範囲を再確認して必要な試験を再実行します。指摘がなければ次へ進みます。発行に支障のある問題が未解決なら発行を保留し、理由を報告します。レビューを理由に無関係な全回帰を一律実行しません。
5. [版更新の判断](#版更新の判断)に従って変更したモジュールを版更新し、既存のpublish.batでそのrepoのpublishへ発行します。発行成功、版・manifest/feed・成果物の整合と、隔離した発行物の起動・変更部分を確認します。未変更Appletの再発行と全体ZIP作成は通常publishに含めません。
6. レビュー対象・結果（指摘なしを含む）、必要な修正と再検証、版更新区分と理由、実行した検証、未実行の回帰、成果物と未確認事項をVERIFICATIONへ記録して、利用者の動作確認へ渡します。コミット・プッシュ・公開・実利用先へのdeployは行いません。

## 版更新の判断

変更したモジュールごとに判定します。次のいずれかを含む場合は、メジャー番号を維持し、マイナー番号を1つ増やしてパッチ番号を0にします（`x.y.z → x.(y+1).0`）。設定項目・保存ファイルの追加や削除は、互換性を保つ変更でも対象です。

| 変更内容 | 判定例 |
| --- | --- |
| 破壊的変更 | 既存の設定・保存データ・公開API・操作契約などとの互換性が失われる |
| 設定項目の追加・削除 | 任意の設定項目を追加する、既存の設定項目を廃止する |
| アプリが保存するファイルの追加・削除 | 新たな保存ファイルを導入する、従来の保存ファイルを廃止する |

たとえば、`0.26.3`に上記の変更を加える場合は`0.27.0`にします。それ以外の通常の実装・修正はパッチ番号を1つ増やし、同じ例なら`0.26.4`にします。ユーザーが対象版を明示した場合は、その指定を優先します。

保存ファイルの追加・削除はアプリの保存仕様の変更を指します。ソースやビルド・テスト生成物の増減、既存仕様に沿った実行時のファイル生成・削除は対象外です。保存ファイル自体の追加・削除がなくても、保存形式などの変更で互換性が失われる場合は破壊的変更として判定します。

同じ変更に複数の条件があっても、マイナー更新は1回だけです。同じ変更の修正・発行再試行・検証用再発行・リリースでは、更新済みの未公開版を重ねて増やしません。レビューや追加修正で区分が変わった場合は、発行前に未公開版の番号を訂正します。影響のないモジュールは版更新しません。文書のみの変更は製品の版更新・発行を行いません。

本体はpackage.json、Appletは各repoの版の正本と関連manifest・プロジェクト/パッケージの版を揃えます。互換性への影響、設定項目・保存ファイルの追加や削除、必要な移行方法は関係する利用者向け文書へ反映し、発行後に成果物・更新情報との一致を確認します。

## 制限付き実行環境

フルアクセスを有効にする前提にはしません。まず許可された環境でローカルツールを使い、権限により失敗する依存確認・.NET発行・Electron実機試験だけ、実行環境の承認機能で同じコマンドを再実行します。通常のWindowsユーザーとしての実行許可と、Windows管理者への昇格は別です。スクリプトから自動昇格・権限変更・セキュリティソフトの停止は行いません。

`dev.bat`は子プロセスの終了コードを保持します。pnpmがSTATUS_STACK_OVERFLOWで終了した場合は、制限環境なら承認付きで同じ処理を試す案内を出します。権限以外の原因もあり得るため、このコードだけで原因を断定しません。自動再試行や別のパッケージ管理ツールへの切替は行いません。設定置換のEPERM、NuGet設定/サービス情報へのアクセス拒否も、失敗ログを保持して通常環境で切り分けます。`dotnet --info`の失敗だけをコンパイル失敗と扱わず、実コマンドの終了結果を確認します。

既存の固定Node/pnpm、`install --frozen-lockfile`、公開後7日の待機、`verifyDepsBeforeRun`、限定されたinstall script許可を維持します。権限エラーを解消するための依存更新、lockfile削除、検査無効化、実行ポリシーの恒久的変更は行いません。製品コード/ビルド手順自体の不具合が再現した場合は原因を修正し、必要な検証を再実行します。

## コミット

1. コミットを依頼されたら、対象変更をレビューし、必要な回帰の一覧を確定します。対象モジュールの標準回帰と、変更した機能のGUI・実プロセス試験を含めます。共通SDK/API・保存領域・依存ツール等を変えた場合は影響する本体/兄弟Appletも含め、無関係な全repoを機械的に実行対象にしません。
2. 必要回帰を実装時の記録と照合し、[再利用条件](#検証結果を再利用する条件)を満たす成功結果は原則再利用します。未実行・失敗・後続変更の影響を受けた試験と、記録不足で照合できない試験だけを実行します。コミットを依頼されたこと自体を再実行の理由にしません。失敗は修正し、影響する試験を再実行します。必要な成功結果が環境依存で揃わない場合はコミットを保留して理由を報告します。文書だけの変更はリンク・差分等の検査を対象とし、製品回帰を実行しません。
3. 修正で製品内容が変わった場合はpublishも更新し、発行物を再確認します。利用者が確認した版からの変更点を伝えます。同じ変更の修正・再発行だけで未公開版を重ねて増やしません。
4. 再利用と今回の実行を合わせて、必要な試験の成功がすべて揃い、最終内容に適用できることを確認してコミットします。別作業の変更を取り込まず、プッシュはリリースまたは明示依頼まで行いません。
5. 再利用元・照合結果・今回実行した項目を以下の証跡へ記録します。実装時に一部だけ確認した場合は不足分を追加し、部分的な成功を必要回帰全体の成功へ読み替えません。

たとえば、設定画面のCSSだけを追加修正した場合は、そのCSSを使う画面の表示確認と必要なビルドを行います。変更したCSSを参照しないAppletの標準回帰は、対象コード・依存・実行条件が同じで成功記録があれば再利用できます。拡張子や変更行数だけで判断せず、試験実装と共通部品・設定・ビルドの依存関係から影響範囲を確認します。

## 検証証跡

実装時から各repoの`.artifacts/`へ検証記録と完全なログを保存し、VERIFICATIONから参照します。既存の試験出力先をそのまま使って構いません。コミット時は`.artifacts/commit-validation-<識別子>/`へ判定をまとめ、元記録・ログを参照します。ログをまとめ直すための再実行や、同じログの複製は不要です。再利用が必要な証跡は通常の古いテスト整理から保護します。履歴文書だけの「成功」や過去チャットは証跡の代わりになりません。

記録する内容:

- 対象repo、検証開始/終了日時、対象変更と必要回帰の一覧、各コマンド・引数・作業ディレクトリ・終了コード、ログのパスとSHA256。
- 実装時に検証した内容を特定するGit tree ID、または試験対象ファイルの一覧とSHA256。後者には試験スクリプト、参照するソース・共有部品・設定・依存/ビルド定義と未追跡fixtureを含め、検証前後で一致することを確認します。コミット未依頼の実装段階で、記録のためだけにstageする必要はありません。入力範囲を特定できない試験は再利用対象にしません。
- コミット対象をstageした後の`git write-tree`と、stage/作業ファイルの一致。試験に関係する未追跡ファイルを記録から漏らさず、別作業をstageしません。再利用元との差分がある場合は、その差分と、各試験への影響・再利用/再実行の判断を記録します。
- コミット後のcommit SHAと`git rev-parse 'HEAD^{tree}'`。最終照合したstage treeと一致させます。検証後に変更があれば再判定します。VERIFICATION等の文書だけの追記は差分と最終treeを記録し、ソース・テスト・設定・依存・ビルド/発行手順の変更を文書のみの例外へ含めません。
- 実際に使用したNode/pnpm/.NET SDK・Runtime/OS/アーキテクチャ、lockfile/toolchain/試験スクリプトの版、試験に影響する環境設定。秘密値をログへ書きません。
- 参照した兄弟repoのcommit/tree、SDK/API、Git管理外の入力/fixtureのSHA256。依存のインストール状態や未管理入力に変更・破損の疑いがあれば再利用しません。
- 発行物を使った試験の場合は、そのEXE/ZIP/manifest/feedのSHA256と実行方式（ソース/発行物、fixture/実サービス等）。

## リリース

1. 本体と同梱対象Appletについて、未コミット変更、未追跡ファイル、branch、origin、対象版、ローカル/リモートcommitを確認します。未コミット変更と未プッシュcommitは別々に確認します。
2. リリース対象の実装にコミット漏れがあれば、上記コミット工程へ戻り、必要回帰・修正・再発行を終えてからコミットします。リリース依頼には、この対象変更のコミットとプッシュを含みます。別作業や帰属不明の変更を自動でまとめず、勝手な破棄・stash・branch切替はしません。対象を分離できない場合は確認してから進めます。
3. fetchでリモートを確認し、対象repoの未プッシュcommitを通常pushします。分岐やリモート側の進みをforce pushで解決しません。リモート先端と検証対象commitの一致を確認します。統合で検証入力が変われば再検証します。
4. 再利用可能な検証を下記条件で判定し、[Release手順](RELEASING.md)で配布物を準備・公開します。公開済み同版は上書きしません。Appletだけ新版になった場合、既公開本体の全体ZIPを差し替えません。新しい全体ZIPも配布するなら、新しい本体Releaseとして準備します。
5. 本体の単一EXE/更新情報/全Applet入りZIPと、未公開同梱Appletの個別更新ZIP/更新情報を公開・検証します。今回公開した各repoの検証成功後に最新3件のReleaseを保持します。通常publish・コミットだけでは公開しません。

## 検証結果を再利用する条件

実装からコミットへの移行では、証跡が残るビルド・型チェック・ソース回帰・同じ発行物の隔離GUI試験等を、試験コマンドごとに判定します。コミットしたこと、作業ツリーがcleanなこと、直前に実行したこと、同じバージョン番号であることだけでは再利用できません。

1. 再利用する試験コマンドが成功し、完全な結果・終了コード・ログを確認できること。失敗したコマンド内の一部成功を、そのコマンド全体の成功として再利用しません。他の必要試験の不足は別に補います。
2. 試験が検証する対象コード、試験自体と関連入力が一致すること。tree全体が一致すれば照合に使えます。コミット前の判定ではtreeに差があっても、その差分が当該試験に影響しないことを説明・記録できれば再利用します。無関係なファイルの変更だけで全試験を無効にしません。影響が不明な範囲は再実行します。
3. コマンド・試験の範囲・設定・依存/ツール・OS等の関連環境と兄弟repoの入力が一致すること。発行物の試験ではEXE/ZIPと配置したファイルのhashも照合します。証跡が不足・消失した場合は該当試験を再実行します。
4. 試験が生成する後続工程の入力が必要なら、その生成物も存在・整合を確認すること。なければ必要なビルドを再実行します。ビルドのやり直しだけをソース回帰の成功に置き換えません。
5. 再利用元、照合内容、再利用した項目、今回実行した項目を今回の証跡へ残すこと。古いログを今回実行したように記録しません。

リリース準備の`typecheck`/`regression`再利用は、[既存のPrepare/seal手順](RELEASING.md#証跡を再利用した準備)に従います。この経路では引き続き検証時と対象のrepo tree全体の一致を要求し、例外は上記の文書のみの差分に限ります。コミット前の試験単位の再利用判定を、そのままリリース証跡の条件充足として扱いません。

新しく発行/梱包したEXE・ZIPに対する起動・更新・復旧・全体ZIPの収録/起動検証、assetのsize/SHA256、公開後の匿名ダウンロードと更新確認は毎回実行します。外部サービスや実機状態を確認する試験も、古い成功を現在の状態とみなしません。再利用できない項目だけを再実行し、無関係な成功済み試験は繰り返しません。

本体の標準`release.ps1 -Mode Prepare`は全項目を再実行します。再利用を選ぶ場合は[証跡を再利用した準備](RELEASING.md#証跡を再利用した準備)に従い、既存のpreflight/sealと配布物検証を維持します。未実装のskipオプションを指定したり、成功記録だけを捏造したりしません。
