# 共通のエラー通知とログ

利用者が実行した処理や、許可されたAPIから受け付けた処理が失敗した場合は、共通のエラー報告経路を使う。画面を開いていないAPI実行でも失敗に気付けるよう、通知基盤の「エラー通知」と本体ログへ同じ原因を出す。機能ごとにエラー用の通知種類を増やさない。

処理失敗が確定していない要確認の状態には[共通の警告通知](warning-notifications-design.md)を使う。エラーと警告は同じ通知基盤・ログを使い、種類別の設定と状態寿命を分ける。

## 利用者向けの設定

「設定 → 通知」のAppDock欄に「エラー通知」を配置する。内部の通知所有者が異なる本体の種類も、一つのAppDock欄へまとめる。

- 初期状態はON、バナーとデスクトップ通知、閉じるまで表示。読み上げはOFF。
- バナーを必須とし、解除や「通知センターのみ」は選べない。デスクトップ通知・Windows通知の追加、表示時間、読み上げは変更できる。
- 通知全体のOFFは設けない。通知とエラーログの両方に残す。
- Applet由来の要求でも、本体が受け付けた処理の失敗は本体が報告する。
- 通知履歴、配送状態、読み上げ、Shellへの表示は[通知基盤](notifications.md)に従う。OSへの受付を、利用者が実際に見たことの証明にしない。

保存先は既存の`notificationPreferences.overrides`。識別子は`ownerKind:host / ownerId:errors / typeId:operation-failed`とし、新しい専用設定ファイルは作らない。

登録定義は`requiredTargets:['banner']`を使う。過去のバナーなし設定は配送時にバナーを補い、旧OFF設定は読込時に破棄する。設定画面を開いただけでファイルを書き換えず、その種類を編集したときに必須先を含めて保存する。

## 報告する失敗と画面内の説明

新規機能・改修では、処理の最終結果が失敗になった箇所を共通経路へ接続する。通知本文は、何が失敗したか、判定できた原因、利用者が次にできることを簡潔に伝える。結果画面とAPIにも同じエラーコード・説明を返し、通知だけを見ないと原因が分からない構成にしない。

入力中の必須項目不足や数値の不正は、その入力欄・ダイアログに表示する。利用者の取消、設定変更による古い要求の取消、通常の停止を失敗として通知しない。権限確認で拒否された外部要求を無制限の通知入口にしない。再試行する設計の処理では、途中の試行失敗と最終失敗を区別する。

この設計を既存のすべての例外・ログへ機械的に適用しない。既存機能の改修時に、通知の必要性、重複、秘密値、取消や復旧の扱いを確認して接続する。

## 共通の実装境界

[ErrorReporter](../src/main/core/error-reporter.ts)を本体内の共通入口とする。発行元は、最終失敗ごとに次の値を渡す。

| 値        | 内容                                                       |
| --------- | ---------------------------------------------------------- |
| `eventId` | 本体で発行した失敗イベントのID。非同期処理はjobId等を使う  |
| `source`  | 本体またはAppletの識別子。ログの発行元                     |
| `title`   | 何の処理が失敗したかを示す短い固定文                       |
| `code`    | 原因を判別できる安全なエラーコード                         |
| `message` | 利用者向けに整えた原因と対処。必要なら実行元の種別を含める |

生の例外、HTTP応答本文、入力データ、共通／追加プロンプト、生成本文、思考本文、APIキー、認証付きURLを渡さない。発行元が既知のエラーを安全なcode/messageへ変換してから呼ぶ。通知本文と保存する履歴にも同じ安全な説明を使う。

ErrorReporterは本体ログへerrorレベルで記録し、TypedNotificationsへ「エラー通知」を発行する。ログには照合用のeventIdとcodeを含める。通知を抑止してもログは書く。通知先・表示時間・読み上げを発行元で固定したり、Windows通知を別経路から直接出したりしない。

同じsource/eventIdの再報告を最大512件の受付記録内で抑止し、通知にも同じ識別子から作るdedupeKeyを渡す。発行元は最終状態を一度だけ確定する。ジョブの状態照会、同一要求の再送、画面の再描画を新しい失敗として扱わない。新たに明示実行した処理が失敗した場合は新しいイベントになる。

通知やログ自体の障害は、元の処理結果を変更したりキューを止めたりしない。通知の発行失敗は安全な説明でログへ残し、エラー通知を再帰的に発行しない。自動の再通知や、選ばれていない通知先への切替も行わない。

この入口は本体内部の部品である。MCP・一般Appletへ任意の本体エラーを発行するAPIを追加したものではない。本体が所有する処理の失敗を呼出元にかかわらず報告する。Applet自身の処理の通知契約を変更する場合は、公開APIとして別途設計する。

## 現在の接続範囲

AI文章生成の**受付済みジョブがfailedになった時点**で接続する。試験画面、Applet、MCPの共通AiServiceから報告し、取得APIや各画面から重ねて発行しない。生成前の入力検証・許可拒否、モデル候補取得の入力中エラーは現在の対象外で、それぞれの戻り値と画面に表示する。

- `AI_OUTPUT_LIMIT`：サーバーが`finish_reason:length`を返した。出力トークン上限または推論の強さの調整を案内する。途中の文章や思考を成功結果として返さない。
- `AI_TIMEOUT`：受付からの期限を超えた。サーバーの状態と待ち時間の確認を案内する。
- 接続、認証、サーバー応答等の失敗：既存の安全なエラーを使う。生の応答から説明を作らない。

Codex連携の接続テスト失敗と、更新確認・適用の最終失敗も接続する。通知には固定の原因・対処を渡し、更新の詳細は更新画面と既存ログへ保持する。接続テストの戻り値には通知と同じ安全な説明を返す。TTS等の既存処理全体を一括移行したとは扱わない。

[設定ファイルの読込・保存・バックアップ・反映・Windows起動設定](settings-sync.md#設定の状態と再起動通知)の障害も、この共通種類へ接続する。`ErrorReporter.episode()`は本体内部で検証したactionを受け付け、同じ障害の原因更新と解消を扱う。原因が変わるごとに安全なログを残すが、期限切れ・閉じる後に同じ障害の通知を復活させない。設定がすべて正常になるとepisodeを終え、AIの単発`report`や別の発行元は終了しない。既存の単発`report`の重複抑止は維持する。

## 確認項目

バナーの解除・センターのみへの変更の拒否、旧OFF設定の無効化、旧設定の編集、ログの維持、読み上げの初期OFF、API実行の最終失敗、同一要求の再送と照会で重複しないこと、取消時の非通知、報告経路自体の障害を確認する。本文とログへ秘密値が混入しないことも検査する。
