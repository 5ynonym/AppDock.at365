# 設定基盤とDefault Shellへの移行設計

実装状態: 段階1の設定基盤は0.26.44で実装・固定EXE確認済み。段階2は0.27.0としてShell移行・部分JSONを実装。Appletインデックスと検索UIは段階3。作業開始時の0.26.43（ホームShell化済み）を基準とする。実装順序は、設定基盤の整理、既存設定画面のDefault Shellへの移行、Appletインデックス・横断検索の追加とする。先に部分JSONを含む3機能の契約を定義する。部分JSONだけは、Shellへ全設定を渡す暫定APIを作らず既存のJSON編集機能を引き継ぐため、Shell移行の完了時に提供する。

設定ページを本体とAppletに共通する入口へ拡張する。左の検索結果から目的の設定へ移動でき、右ではその設定を含むページ全体を編集できる。Applet詳細の設定タブも残し、どちらの入口でも同じ画面・下書き・保存結果を使う。

## 対象と既存仕様

対象は設定の項目定義、共有編集セッション、設定ページ全体とApplet詳細の設定本文のShell描画、ページ単位のJSON編集、設定検索と項目への移動。Applet詳細の説明・ショートカット・ログの構成、設定保存先、起動や入力処理の意味は維持する。

移行前（0.26.43）と新しい設計を区別する。

| 移行前 | この設計での変更 |
| --- | --- |
| `useSettingsEditor`が本体rendererで下書き・全体JSON・revision・保存を共有 | 編集状態の正本を本体mainのサービスへ移し、rendererのフックは購読・操作のアダプターにする |
| 本体カテゴリ・表示・変更マークの判定が`main.tsx`に分散 | カテゴリと項目のカタログ、JSONの対象範囲、変更判定を共通化する |
| Appletは`SettingDefinition`と専用部品で設定を表示 | 宣言を再利用し、移動先・検索情報と共通設定項目を補う |
| JSONモードは全`settings.json`を編集 | 選択ページが扱う部分を編集する |
| 設定ページにApplet別設定の入口を置かない | Applet詳細を維持し、設定ページにも同じ設定本文への入口を置く |
| Applet設定の検索は本文を絞り込む | 横断検索は左に結果を出し、右はページ全体を表示する |
| Shellの本文契約は`page.logs`と`page.home` | 設定用のモデルと操作を追加し、全体ページと詳細内で共用する |

本設計の段階1・2の実装は、[設定パネルの共用](host-development.md#applet設定パネルの共用)と[Shellのページ表示](shell-pages.md)を拡張する。段階3は後続。Shellの共通経路と依存境界は[Shell基盤](shell-foundation.md)、保存分類は[設定同期](settings-sync.md)、操作許可は[共通操作API](appdock-api.md)を正本とする。

## 画面と操作

### 設定インデックス

設定ページの左上に検索欄を置く。空欄では既存順の本体カテゴリに続けて「Applet」の見出しとApplet一覧を表示する。Appletの表示順は既存`appletOrder`の解決処理を共用し、ここに新しい並べ替え機能は追加しない。無効・停止中も設定を開ける。宣言済み設定がなくても、表示方法・開始遅延などの共通設定があれば表示する。

個々のWebAppletも同じインデックスに含め、既存の個別設定本文を表示する。追加・削除・新規サイトのショートカット初期値を扱う組み込み「WebApplet」管理項目は管理画面の入口に残し、今回の設定インデックスには複製しない。Default Shellも実在する設定に従って扱い、固定名による特別な検索項目を作らない。

右には選択ページの見出し、共通保存欄、フォームとJSONの切替、設定本文を置く。Applet選択時はその名前を示し、詳細ページの設定タブと同一の本文を使う。全体ページだけが左のインデックスを持ち、詳細タブには追加しない。

### 検索と移動

- 入力中は左を検索結果一覧に切り替える。入力だけでは右の選択やスクロール位置を変えない。結果0件でも右は保持する。
- 結果は設定項目単位とし、項目名と「本体カテゴリ」または「Applet名」を表示する。操作ボタンや管理画面へのリンクも項目として検索できるが、検索・選択だけで操作を実行しない。
- 検索対象は名前・説明・設定キー・所属名・明示した検索語・静的な選択肢のラベル。現在の入力値、認証情報、ファイル内容は検索しない。動的選択肢や配列の個々のデータ行は初版の全文検索対象にしない。
- 検索語と対象文字列をUnicode NFKCと小文字化で正規化し、空白区切りの語をANDで照合する。名前の完全一致、名前の部分一致、その他の一致の順に優先し、同順位はカテゴリ・Applet・項目の表示順で安定させる。新たな検索ライブラリは前提にしない。
- 結果クリックまたはキーボード選択後のEnterで、そのページのフォーム全体を開く。該当部分の折りたたみを展開し、必要な描画完了後にスクロールして項目を強調する。固定ヘッダーで隠さない。
- 強調は約2秒で解除し、連続選択では最後の移動だけを有効にする。動きを減らす設定では即時スクロールと静的な強調を使う。フォーカスは項目の見出しまたはコンテナへ移し、入力操作やボタン実行を自動開始しない。
- 検索欄の上下キーから結果を選択でき、Escapeで検索を解除する。IME変換中のEnter/Escapeを検索操作として処理しない。結果件数・選択状態・移動完了を支援技術でも判別できるようにする。
- 検索を消すと通常のインデックスへ戻り、右で開いているページの選択を示す。検索文字列は同じ起動中のページ往復とShell復旧では保持し、共有設定ファイルへ保存しない。

Applet設定本文の既存ローカル検索は、この移行で両入口から除く。設定横断検索から来た項目が隠れる状態を作らない。ショートカットやジェスチャー等の専用一覧内検索は維持し、横断検索は初版ではその一覧・設定ブロックへ移動する。全コマンドや全配列行を設定検索へ重複登録しない。

非表示のページをあらかじめ描画してDOMから検索しない。検索後にAppletが削除された場合は結果を更新し、古い移動要求には対象消失を返す。無効項目も理由とともに表示し、検索のためにAppletを起動しない。

### 保存とJSON編集

「保存」「変更を破棄」は従来どおり全ページの未保存編集が対象。JSONが一部分だけでも「このページだけ保存」へ意味を変えず、保存欄で全編集内容が対象であることを示す。カテゴリとAppletの変更マークは、同じカタログの範囲定義から求める。

JSONの範囲は選択中のページで決まり、画面内に見えている行、スクロール位置、検索語では変わらない。フォームと同じ下書きを表示し、必要な親キーを残した部分オブジェクトとする。例えば「表示」のJSONは`host.theme`と`host.shellProvider`だけを含む。全体JSONを別の編集正本として残さない。既存の「ファイルを開く」は実ファイルを開く操作として維持する。

## 設定カタログ

カタログは表示用メタデータと、ページが扱う設定・操作の対応を本体側で管理する。型や値検証は既存の設定定義を再利用し、検索用とフォーム用にタイトル・説明の別リストを持たない。本体の専用フォームもこのカタログから項目IDとラベルを取得する。すべてを汎用フォームへ変換する必要はない。

| 定義 | 主な情報 |
| --- | --- |
| ページ | 安定ID、タイトル、所有元、並び順、描画種別、JSON対応の有無、項目一覧 |
| 項目 | 安定ID、ページID、タイトル、説明、検索語、型、適用タイミング、利用不可理由、移動先 |
| データ範囲 | 本体内の読取・更新アダプター、許可キー、配列の選択規則、削除規則、検証、変更判定 |
| 操作 | 本体が発行する操作ID、入力契約、必要な確認、可否、完了の意味 |
| 移動先 | 項目ID、必要な展開先、複合コントロール内の対応箇所 |

IDは表示名や配列の添字から作らず、所有元と安定キーから作る。Applet IDや設定キーにドットが含まれても壊れないよう、データパスはセグメント配列や専用アダプターで扱う。任意文字列のドット分割を更新権限の根拠にしない。

Appletの`settings`、`settingActions`、ページ表示方法、開始遅延をカタログへ変換する。既存`aliases`は保存互換の用途を確認して扱い、検索語追加のために意味を変更しない。検索語が必要なら独立した任意メタデータとして追加する。既存manifestを必須変更にせず、既存の名前・説明・キーだけでも動作させる。

MCP向けの`automation: true`は外部操作の公開条件であり、画面に表示・検索できる項目の条件として流用しない。検索カタログの追加だけでMCPや通常Appletへ公開範囲を広げない。

## ページとJSONの対応

次表を初期の対応とする。実装の段階1で現行フォームの全項目を照合し、各キーの所属・重複・削除規則を試験で固定する。親オブジェクト全体を無条件で編集範囲にしない。

| ページ | 部分JSONの範囲 |
| --- | --- |
| 表示 | `host.theme`、`host.shellProvider` |
| 一般 | `host.startAtLogon`、`runAsAdministrator`、`closeToTray`、`notifications`、`hardwareAcceleration`、`startMinimized`。いずれも`host`配下 |
| リボン | `ribbon` |
| タスクトレイ | `trayMenu`、`host.trayClickCommand`、`host.trayDoubleClickCommand`。旧派生値は既存変換処理が管理 |
| ショートカット | 現行の`keybindings`を正本とする範囲。旧互換・派生フィールドは既存変換処理が管理 |
| マウスジェスチャー | `gestures` |
| プロフィール | `profile`内のフォームで編集できる項目。画像バイナリや一時URLは含めない |
| バージョン情報・更新 | `updates`と各Appletの`updateSource`。実行環境・確認結果・進捗は含めない |
| 通常Applet | `extensions[ID].settings`、`startupDelaySeconds`、宣言ページに対応する`pages`。有効状態・更新元・別Appletの値は含めない |
| 個別WebApplet | `webApplets.items`の対象IDのうち、個別フォームで編集する名前・URL・アイコン・表示方法・遷移規則・許可origin・アカウント参照。IDは読取専用、対象外項目は保持 |
| Webアカウント・操作の許可・Codex連携 | 初版はJSONなし。既存の別保存・即時反映を維持し、検索とフォームを提供 |

部分JSONは全設定用`parseSettings`へ直接渡さない。対象範囲を検証した後、共有下書きの対象部分だけを更新し、保存時に既存の全体検証を行う。範囲外キーや読取専用値の変更はエラーにし、黙って捨てない。対象外の未知キーと未導入Appletのデータを保持する。

オブジェクト範囲では、表示された編集対象のキーを省略するとその範囲内の削除とする。必須値はエラー、既定値を持つ任意値は既存規則に従う。フォームにない未知キーは削除対象にしない。自由JSONとして宣言された項目とApplet自身の`settings`内容は、その項目の検証に従って内部キーの追加・削除を扱う。

配列は範囲が配列全体なら並びと削除を含めて更新する。特定Applet・WebAppletだけを扱う場合は安定IDで対象を照合し、他IDの要素・順序・対象外フィールドを保持する。対象削除を部分JSONの配列省略で代用せず、既存の管理操作へ限定する。

### 不正な入力と画面切替

編集中のJSONテキストと最後に検証できた下書きを別に保持する。有効な部分JSONは対象範囲へ原子的に反映する。不正な場合は生テキストとエラーを保持し、保存を止める。

初版は不正なJSONがある状態で、別カテゴリ・別Applet・フォーム・検索結果への設定内移動を成立させない。元の編集場所で修正または既存の確認付き全体破棄を行う。検索入力自体はできるが、移動を拒否した場合は選択を変えず理由を表示する。設定以外のページへは離れられ、未保存通知から元のJSON編集位置へ戻れる。別入口で同じ範囲を上書きしない。

これは複数の不正JSONとフォーム下書きを同時に持つ複雑さを避けるための初版の制約。検索で移動を試みたことを、JSONを捨てる同意として扱わない。

## 編集セッションと保存の責務

本体mainに`SettingsEditingSession`を置き、primaryコンテキストに1つ保持する。クラス名は実装候補だが、所有権は固定する。ShellのViewや本文Controllerが終了してもセッションを破棄しない。終了・再起動をまたぐ下書きの永続化は今回の範囲外とし、既存の終了動作を維持する。

| 所有者 | 責務 |
| --- | --- |
| `SettingsStore`と既存機能サービス | 保存済み設定、revision、原子的保存、既存の副作用と即時反映操作 |
| `SettingsEditingSession` | 全体の下書き、入力バッファ、画像の未保存状態、基準revision、検証、dirty、保存・破棄の実行管理 |
| 設定の内容Controller | ページ選択、検索結果、対象項目、公開モデル、許可された操作への振り分け |
| `ShellPageHost` | View・領域・提供元・IPC送信元・ready・フォーカス・復旧。設定固有判断を持たない |
| Default ShellとShell Applet | 描画、IME入力、スクロール、強調、フォーカス。保存や業務処理を独自実装しない |
| 本体rendererの編集アダプター | 未移行のショートカット・詳細ヘッダー・通知等を同じセッションへ接続 |

保存revision、編集revision、表示モデルrevisionを分ける。編集操作にはセッションID、操作ID、基準の編集revisionを付け、古い表示からの更新を検出する。クライアントは入力順を保ち、保存・移動前に確定済み入力の受付を待つ。古い応答で新しい入力を上書きしない。同じ操作の再送で保存・外部操作を二重実行しない。

文字入力中の空文字・未完成の数値等は項目ごとの生テキストとして扱い、`NaN`や関数をIPCモデルへ載せない。IMEの変換途中は表示側で保持し、確定後に本体へ渡す。Shell復旧時は本体が受付済みの編集・JSON・画像・選択を復元する。未送信のIME変換途中まで復元できるとは扱わない。

外部の保存済み設定が変わった場合、未編集なら追随し、未保存なら基準revisionと下書きを保持して競合を通知する。初版は自動マージせず、既存の競合検出と確認付き破棄・再読込を使う。即時反映項目は共有下書きへ混ぜず、失敗や再取得中の状態も独立して扱う。

プロフィール画像は本体が管理する一時データと参照を使う。Shellへローカルの任意パスやバイナリ全体をモデルとして配信しない。破棄・置換・終了時に一時データを回収する。

## Shellの領域と公開契約

設定用領域の候補名を`page.settings`とし、表示文脈を「全体設定」と「Applet詳細の設定」に分ける。全体設定では左インデックス・検索・右本文・保存欄を単一Viewで描画する。本体の設定用サイドバーを同時に残さず、リボンとタイトルバー・共通ステータスバーの内側に1つの表示枠を確保する。既存の本体サイドバーを跨ぐため、段階2の最初に領域・最小幅・リサイズ・フォーカスを実証する。

Applet詳細では本体の一覧・見出し・タブ・共通保存欄を保ち、設定タブの本文枠だけに同じ領域を置く。モデルの文脈で左インデックスと重複する保存欄を出さない。設定本文はDefault Shell内の同じ部品を使い、本体の旧`AppletSettings`を復旧用に残さない。ショートカットタブの移植は今回必須にせず、共有編集アダプター経由の連携を維持する。

公開モデルにはセッション識別子、表示revision、編集状態の要約、ナビゲーション項目・検索結果、選択ページの定義と値、JSON範囲、入力エラー、利用できる操作、移動要求を含める。全体下書き、別ページの値、認証token、内部関数、React要素は渡さない。別Shellも同じ公開型とbridgeだけで描画できるようにする。

| 操作群 | 入力と本体側の検証 |
| --- | --- |
| 選択・検索・項目移動 | カタログ中のページID・項目ID、検索文字列。対象消失と不正JSONによる移動不能を判定 |
| 項目編集・JSON編集 | 登録済み項目IDまたは範囲ID、値またはテキスト、編集revision。型・範囲・長さ・対象文脈を検証 |
| 保存・破棄・再読込 | 同じ共有セッションへ接続。pendingと操作IDで重複を防止し、既存確認を維持 |
| 設定内の操作 | 本体がモデルで発行した操作IDと規定の引数。選択肢取得、素材選択、アカウント操作、更新等の既存サービスへ接続 |
| 描画完了・移動完了 | 現在のページIDと移動要求ID。古い検索結果から届くスクロール・強調を破棄 |

設定用bridgeは、選択されているShellの該当View・main frame・現在のページ・セッションにだけ結び付ける。自己設定APIとは別の、設定UIを描画するための権限として定義する。通常AppletのworkerやリモートWebページへこの操作権限を渡さない。GUI操作にMCPの許可を要求する仕様へ変更せず、MCP側の許可を迂回する新しい外部APIも追加しない。

Shellから任意パス・任意コマンドID・全設定オブジェクトを渡して実行する入口は作らない。Appletの設定アクションは対象Appletの宣言済み操作と実行可否を本体で再確認する。破壊的操作の既存確認、PC専用権限の保存境界、停止中の利用不可理由を維持する。

Default ShellとShell Appletは同じ公開契約と実行経路を使う。移動する表示部品は`Shell`側へ所属を移し、`src/renderer`や`src/main`の内部importで共用しない。専用bridgeの操作数が多い場合も機能ごとの既存サービスを呼び出し、`ShellPageHost`へ個別設定処理を追加しない。

未提供領域と故障時は同じ編集セッションを使ってDefault Shellへ復帰する。設定保存に伴うShell自身の切替でも、保存完了と表示の再接続を別に扱い、古いViewの完了通知を新しいViewへ適用しない。共通設定通知・オーバーレイの重なり順とTab移動、safe起動の契約は既存Shell基盤に従う。

ホーム移行後も、編集状態の正本はこの計画の段階1で移す。現行ホームは共有editorからApplet表示順だけを読み取り専用に投影し、保存や第二のdraftを持たない。段階1ではその入力をmainの共有編集サービスへ接続し直す（[ホーム契約](shell-pages.md#ホームの契約)）。

## 実装の段階と完了条件

### 段階1 設定基盤の整理

カタログと範囲定義、純粋な部分JSON変換・検証、安定IDと検索モデル、mainの共有編集セッションを用意する。既存画面はアダプターでつなぎ、現在の操作を維持する。将来の部分JSONや検索のUIはまだ載せない。

完了条件は、既存の設定・Applet詳細・WebApplet管理・ショートカット・ジェスチャー・プロフィール・未保存通知が1つの編集状態で動くこと。範囲外のデータ保持、revision競合、非同期入力順、画像、保存失敗を関連試験で確認する。カタログ上の全ページと現在の項目を照合し、欠落や意図しない重複を解消する。

### 段階2 既存設定画面のDefault Shell移行

最初に公開契約と領域の接続を実証し、その後、既存設定ページの全カテゴリとApplet詳細の設定本文を移す。即時反映画面、専用編集部品、ファイル選択、確認dialog、設定アクションも同じ契約に接続する。段階中にカテゴリを順に移せるが、段階の完了時に移行済み描画を本体へ残さない。

完了条件は、従来の設定操作がDefault Shellと公開契約だけを使うShell fixtureで成立し、復旧・切替で受付済み編集が保持されること。全体設定の左右領域、詳細内の枠、フォーカス、未保存通知を実画面で確認する。JSON編集は段階1の範囲定義を使う部分JSONへ置き換え、この段階の完了時に提供する。旧全体JSONの画面は撤去し、Shellへ全設定を配信する暫定APIを作らない。詳細タブにもフォームと部分JSONの切替を用意し、両入口で同じ不正入力の修正ができるようにする。

### 段階3 機能拡張

Appletインデックス、横断検索と項目移動を順に提供し、本文のローカル検索を整理する。段階2の部分JSONをそのまま新しい入口でも使う。両入口の同一本文、全体保存、検索からの移動、不正入力の保持を一連のGUI操作で確認する。

各実装段階は[共通手順](development-workflow.md)に従い、完成した本体を版更新・本体publish・固定EXE確認まで行う。今回の設計文書作成は製品変更・版更新・発行に当たらない。commit・push・Release・実利用先deployの範囲は各依頼に従う。

## 実装開始時に確定する事項

進める順序、編集セッションの所有権、両入口の共用、JSONの更新境界、検索の基本動作は本設計を基準にする。APIの正確な型名・操作名・サイズ上限、カタログの全キー表、専用コントロールごとの移動先は、段階1の型設計と段階2の領域実証で確定し、この文書へ反映する。新しい必須manifestや依存追加、保存形式の全面変更、複数Window、未保存入力の再起動後復元は前提にしない。

### 段階1で確定した内部契約

`SettingsEditingSession`をprimaryに1つ設け、`SettingsEditingState`と`SettingsEditRequest`を本体renderer専用IPCで取得・更新する。これはShellの公開モデルではない。`sessionId`、`operationId`、`editRevision`で古い入力を拒否し、直近512操作を再実行しない。保存revisionはSettingsStoreのrevisionを別に保持する。JSONはUTF-8で1MiB、画像は従来どおり5MiBが上限。終了をまたぐ下書き永続化は追加しない。

ページと許可パスは`src/shared/settings-catalog.ts`の`settingsPaths`を正本とする。安定項目IDはページIDとキーを個別にURL符号化して結合し、実データの更新はセグメント配列で行う。部分JSONはページを既定設定上で検証して、許可した葉だけを元のdraftへ戻す。Appletのsettings内部は自由なキーの追加・削除を許可し、宣言済み値は既存検証を適用する。WebApplet配列は対象IDの1要素のみを受け付け、他ID・enabled・imported等は保持する。

ホームの順序入力はmainの編集サービスから直接取得する。既存requestのappletOrderは互換性のため受け付けるが、実ホストでは編集サービスの投影を優先する。段階1ではUIの全体JSONを維持し、部分JSONの変換基盤だけを追加する。
## 実装時に確定した契約

編集の正本はSettingsEditingSession、公開投影はSettingsPageSession / SettingsPageModel / SettingsPageAction。settings-catalog.tsがページ・項目ID・JSON範囲・変更判定を定義する。IDはページIDとキーを個別にencodeURIComponentして結合し、階層は文字列分割せずキー配列で扱う。JSON上限はUTF-8 1MiB、画像5MiB、操作再送履歴512件。

ホームShell化に合わせ、ホームのappletOrderもmainの共有編集から読み取る。ページ寿命を管理するShellPageHostへ設定固有の判断を入れず、requiresFlushのControllerだけView切替前に入力完了を待つ。フォーム部品はsrc/shared/settings-ui、設定専用本文はshells/default/settingsへ分離した。保存ファイル・操作許可・即時保存先は追加変更しない。
